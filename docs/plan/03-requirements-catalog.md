# 03. Requirements Catalog

This catalog is the identifier source for the whole plan. Every requirement in the three brief files (`docs/brief/01-master-brief.md`, the appendices under `docs/brief/02-appendices/`, and `docs/brief/03-reference-architecture.md`) appears here once, with an identifier, a tier, an owning service, a source, the workflow or rule it depends on, and an acceptance criterion. Every later plan document cites these identifiers and never restates a requirement in its own words: the service sheets in `06-services/`, the roadmap in `17-roadmap.md`, the traceability matrix in `20-traceability-matrix.md`, and the work breakdown in `34-work-breakdown.md` all point back here.

**How identifiers are assigned.** `REQ-<AREA>-<NNN>`, with the area codes from Appendix L: the twenty-two service areas (IDN, PLT, SCH, ADM, ACA, ASM, SCD, ATT, FIN, COM, NOT, RQS, DOC, BEH, RPT, AUD, WEL, HR, OPS, AI, GW, BFF) and the fourteen cross-cutting areas (SEC, PRV, PERF, L10N, UX, WEB, MOB, API, INT, DATA, MSG, INF, TST, PLAT). Numbers run from 001 within each area, in the order the rows appear. The Requests service uses `RQS`, so a requirement about it reads `REQ-RQS-001`. A number is never reused and never skipped; a withdrawn requirement keeps its row with the word "withdrawn" and an ADR reference in the Requirement column.

**How to add one.** Append the next number in the area. Cite the brief section or appendix that demands it; a requirement with no source is scope nobody asked for and is refused. Give it a tier, a workflow or rule from Appendices R and S where one applies, and an acceptance criterion in Given, When, Then form or a real test case identifier. Then update the traceability matrix in the same session.

**Nothing here is optional.** Master brief Section 1 states that a plain statement of what the system does is a MUST, and Section 13 states that Appendix A is normative. Tier 1 rows are built first and finished completely. Tier 2 rows are extended scope and start only when Tier 1 is complete and polished. Tier 3 rows are designed for in the data model and extension points and built last. A tier is a sequencing decision, not a permission to skip.

## How to read a row

| Column | Meaning |
|---|---|
| ID | `REQ-<AREA>-<NNN>`, sequential within the area |
| Requirement | One behaviour, stated so that a test can pass or fail it. Compound sentences from the brief are split into one row each |
| Tier | 1, 2 or 3 from the source. An Appendix A item with no tier mark is Tier 1. A service listed as Tier 2 in Appendix L makes its rows Tier 2 unless the source marks them Tier 3 |
| Service | The owning service by its canonical short name from Appendix L, `Bff.Web` or `Bff.Mobile` for the backends-for-frontends, `Gateway`, or `cross-cutting` when the behaviour is a rule every service obeys |
| Source | The master brief section (for example "Master brief Section 10.2") and the appendix item (for example "Appendix A10") that demand the behaviour |
| Workflow / Rule | Real identifiers from the index tables of Appendix R (`WF-`) and Appendix S (`BR-`), or "none" |
| Acceptance | A real test case identifier from Appendix Q, Appendix R, Appendix V or Appendix W where one matches the behaviour exactly, otherwise a one-line Given, When, Then with a concrete number. Document 20 turns every one of these into a test case identifier |
